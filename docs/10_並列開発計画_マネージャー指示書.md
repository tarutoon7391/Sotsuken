# 並列Claude Code 開発計画（マネージャー指示書）

> 目的：卒研アプリのMVPを、Claude Codeを複数タブ並列で起動して一気に試作する。
> 本番コードではなく「並列開発の効率検証」兼「動くプロトタイプ」。
> 体制：ワーカー5タブ＋マネージャータブ1本＋設計判断チャット。トーンさん＝タブの起動・初期プロンプト投入・マージ実行・最終判断。
> タブ同士は Claude Code の**クロスセッションメッセージング**で連絡する（Windows は v2.1.234 以降。手元は 2.1.292 で確認済み）。

---

## 0. フェーズ0で確定したこと（2026-10-07。ワーカーは最初にここを読む）

- **DB は Docker ではなく Railway の MySQL** を使う。接続文字列は `.env` の `MYSQL_URL`。**migrate はトーンさんだけが流す**（ワーカーは `npm run migrate` を実行しない。`.claude/settings.json` で deny 済み）
- **フロントは `client/`（Vite + React）**。`public/` は仮トップだけ。デザインは `docs/design/` の HTML モックに合わせ、色・余白は `client/src/styles/broadsheet.css` の変数から取る
- **契約は `shared/`（`@sotsuken/shared`）**：`constants.js`（ロール・状態・エラーコード・既定値・ルーム名）、`socket-events.js`（イベント名）、`api-types.js`（JSDoc 型）。サーバーは `require('@sotsuken/shared/constants')`、クライアントは `import ... from '@sotsuken/shared/constants'`
- **REST のスタブは全エンドポイント登録済み**（501 `NOT_IMPLEMENTED`）。認証・ロール・クラス所属のミドルウェアも適用済みなので、各担当はハンドラの中身を書くだけ。`routes/index.js` と `app.js` は触らない
- **Socket の土台**：`sockets/index.js` が接続時の認証・`lesson_id` 検証・ルーム join（全員／先生／生徒）まで行う。ハンドラは `sockets/handlers/*.js` に置けば自動で読み込まれる。REST やジョブから送るときは `sockets/io.js` の `emitToLesson / emitToTeachers / emitToStudents`
- **ジョブの土台**：`jobs/*.js` に `{ name, intervalMs, run }` を export すれば自動で読み込まれる
- **アクセス権の判定は `services/access.js`**（`getClassAccess / getLessonAccess`）。自前の所属チェックを書かない
- **package.json の依存は先に入れてある**（bcrypt / multer / express-session / livekit-server-sdk / jest / livekit-client / socket.io-client / react-router-dom）。ワーカーが依存を足す必要はほぼ無い。足すときは @manager に一言
- **ポートは worktree ごとに変える**（`.env.example` の表）。`.env` は git 管理外なので worktree ごとにコピーする
- **Claude Code の許可リスト**は `.claude/settings.json` にコミット済み（npm / node / git の読み取り系 / curl は許可、push・merge・migrate・railway は拒否）
- **仕様の補足（04 のとおり）**：`PUT /lessons/:id/spotlight` は `routes/token.js`（W3）に置く。`GET /lessons/:id/chat` と `GET /lessons/:id/understanding` は `routes/chat.js` / `routes/understanding.js`（W2）

## 1. 全体の流れ

```
フェーズ0（1タブ・直列）      フェーズ1（5タブ・並列）              フェーズ2（1タブ・直列）
┌──────────────┐   ┌──────────────────────────┐   ┌──────────────┐
│ 土台を作る     │→ │ W1 認証/クラス/授業 API    │→ │ 結合・通しテスト│
│ ・リポジトリ    │   │ W2 出席/確認/理解度/質問  │   │ ・マージ順に統合 │
│ ・DB/マイグレ   │   │ W3 LiveKit基盤           │   │ ・E2E動作確認   │
│ ・サーバー骨格  │   │ W4 生徒画面              │   │ ・バグ潰し      │
│ ・契約ファイル  │   │ W5 先生画面＋共通画面     │   └──────────────┘
└──────────────┘   └──────────────────────────┘
   完了（phase0 タグ）        目安 2〜3時間（並列）              目安 1〜2時間
```

**鉄則**
0. **命令の出どころは3層**（§5）。初期タスクはトーンさん、途中の裁定はマネージャータブ、設計判断は設計チャット
1. フェーズ0が終わるまでフェーズ1は始めない（契約が無い状態で並列すると全員ズレる）
2. 各ワーカーは **git worktree で別ディレクトリ・別ブランチ**。同じ作業ツリーを2タブで触らない
3. ワーカーは **自分の担当ディレクトリ以外を編集しない**（§3 の所有権表）。他領域に手を入れたくなったら「依頼メモ」を `docs/requests/` に書いて止まる
4. 契約ファイル（`shared/` と `docs/04`）はフェーズ1中は**凍結**。変更が必要ならマネージャーに相談

### P1：W1 認証・クラス・授業・資料 API

```
【ゴール】04_API仕様の「アカウント」「クラス」「授業」「資料・添付」のエンドポイントを実装し、スタブ(501)を本実装に置き換える。

【担当範囲】server/src/routes/{auth,classes,lessons,files}.js、server/src/services/{auth,classes,lessons,files}.js、scripts/smoke-w1.sh

【手順】
1. auth：register/login/logout/me/me(PUT)/me/icon。bcryptでハッシュ、express-session でセッション（req.session.user = {id,name,role}）
2. classes：作成（join_code 8桁英数字をユニーク生成）、一覧、join、GET :id（join_code は先生のみ、live_lesson_id）、members
3. lessons：作成（title, tags[] → tags/lesson_tags にupsert、room_name を生成）、一覧（?tag= 絞り込み、material_count）、tags一覧、start（同一クラスにliveがあれば409 ALREADY_LIVE をトランザクションで保証。lesson:started を emitToLesson で送る）、end（ended_at。出席確定は services/attendance.js の関数を呼ぶ想定で TODO と docs/requests メモ。lesson:ended を送る）、PATCH、GET詳細
4. files：multer でアップロード（ALLOWED_UPLOAD_MIMES、FILE_MAX_BYTES）、kind=material は先生のみ、一覧、DELETE（アップロード者のみ、ファイル本体も削除）。保存先 config.uploadDir、url は /uploads/<ファイル名>
5. ミドルウェアはスタブに適用済み。足りなければ追加してよいが middleware/ 自体は編集しない
6. 動作確認スクリプト scripts/smoke-w1.sh（curlでregister→login→class作成→lesson作成）

【制約】CLAUDE.md準拠。エラーコードは shared/constants の ERROR_CODES。Socket送信は sockets/io.js 経由。LiveKit・出席系は触らない。
```

### P2：W2 出席・確認ボタン・理解度・質問・チャット（REST＋Socket＋ジョブ）

```
【ゴール】出席（累積方式）・確認ボタン・理解リアクション・質問箱・チャットのREST/Socket/タイマーを実装する。

【担当範囲】server/src/routes/{attendance,attention,questions,understanding,chat}.js、同 services、server/src/sockets/handlers/*.js、server/src/jobs/*.js（index.js 以外）、テスト（*.test.js）

【手順】
1. 出席（03_DB設計 §attendance の状態遷移・判定SQLをそのまま実装）
   - handlers/attendance.js：接続成功 → present（lesson が live のときだけ attendance をupsert）、切断 → away（away_since記録）
   - POST away / POST return：return は WHERE status='away' の条件付きUPDATEで away_total_sec に今回分を加算。閾値以上なら absent にして 409 ALREADY_ABSENT
   - GET attendance（先生：クラス全生徒、未入室は absent/joined_at null、remaining_sec を計算）、GET attendance/me（生徒）
   - PATCH 手動修正
   - jobs/attendance-timer.js：1分間隔、`away_total_sec + TIMESTAMPDIFF(SECOND, away_since, UTC_TIMESTAMP()) >= away_timeout_min*60` を absent に更新し、attendance:update を先生に送る
   - 授業 end 時の確定処理 finalizeAttendance(lessonId) を services/attendance.js から export（W1 の end から呼ぶ。呼び出し自体は結合時に繋ぐ）。開始時に接続中の生徒を present にする markPresentOnStart(lessonId) も同様に export
2. 確認ボタン：POST 発動（deadline=now+timeout_sec）、自動発動設定（jobs/attention-auto.js）、respond（REST と Socket 両方。deadline超過は409 CHECK_EXPIRED）、GET 応答状況。attention:check を生徒に、attention:update を先生に
3. 理解リアクション：understanding:send を受けて保存→先生に understanding:update（リセット以降の各生徒の最新1件を SQL で集計）。understanding:reset（先生）で lessons.understanding_reset_at 更新→全員に understanding:reset。GET understanding（current/totals）
4. 質問：POST（body省略＝挙手）、GET（匿名は先生以外に user を含めない）、PATCH answered。Socket: question:raise → question:raised（先生）、question:new / question:answered
5. チャット：chat:message の受信→保存→ルーム全員に配信（file_id があれば files を JOIN）。GET chat（before/limit）
6. 単体テスト（jest）で累積判定のケース：14分→復帰→再退出→1分で absent。DB を使うテストは MYSQL_URL が無ければ skip

【制約】イベント名は shared/socket-events.js から。宛先振り分けは socket.data.role と sockets/io.js のヘルパで。sockets/index.js・jobs/index.js は触らない。LiveKitは触らない。
```

### P3：W3 LiveKit基盤

```
【ゴール】LiveKit を使った映像基盤を、サーバー（トークン発行）とクライアント（接続・publish・subscribe）の両面で実装する。生徒映像は先生のみ購読可、スポットライトで全員に開放。

【担当範囲】server/src/routes/token.js、server/src/services/livekit.js、client/src/livekit/*、docs/livekit-notes.md、docs/requests/w3-components.md

【手順】
1. server：POST /api/lessons/:id/token
   - livekit-server-sdk で AccessToken 発行（identity は "user:{id}"）。先生：canPublish/canSubscribe 全許可。生徒：canPublish=true、subscribe は購読制御に委ねる。レスポンスは shared/api-types の TokenResponse
   - LIVEKIT_* 未設定なら url 空で返す（クラッシュさせない）
   - PUT /api/lessons/:id/spotlight：lessons.spotlight_user_id 更新→ sockets/io.js の emitToLesson で spotlight:update
   - 生徒映像の購読制御：LiveKit の setTrackSubscriptionPermissions（publisher 側で許可先を指定）を使い、生徒の publish 時は先生の identity のみ許可、スポットライト時は全員許可に切り替える関数を client 側に用意
2. client/src/livekit/（README.md のファイル構成どおり）
   - useLiveKitRoom.js / TeacherPublisher.jsx / StudentCamera.jsx / RemoteVideo.jsx / StudentGrid.jsx
3. docs/livekit-notes.md：購読制御の仕組みと、本番VPS移行時の差分（URL差し替えのみ）

【制約】pages/ は触らない（部品を export するだけ。W4/W5 が組み込む）。部品の props は docs/requests/w3-components.md に書き、確定したら @w4-learn と @w5-teach に1通ずつ送る。
```

## 5. 命令系統とセッション間連絡のルール

### 誰が何を命令するか（3層）

| 層 | 誰 | 命令する内容 | 手段 |
|---|---|---|---|
| 1 | **トーンさん** | 初期タスク（P1〜P6 の投入）、タブの起動・終了、マージの実行、migrate、最終判断 | プロンプトを貼る。タブは人間しか起動できない |
| 2 | **マネージャータブ（@manager）** | 途中の裁定：契約変更の可否、ブロッカーへの対処指示、結合時の繋ぎ込み担当 | ワーカーへ @名前 でメッセージ |
| 3 | **設計チャット（Claude）** | 設計判断、プロンプト作成、マネージャータブへの指示文 | トーンさん経由 |

ワーカーは **@manager からの指示は従う、他ワーカーからの連絡は参考情報**として扱う。
マネージャータブは**設計を変える権限を持たない**。契約変更のうち「誤記・不整合の修正」レベルは即断してよいが、仕様判断が要るものは「トーンさんに確認」と返して止まる。

### メッセージの経路（増やしすぎない）

| 種類 | 経路 | 備考 |
|---|---|---|
| 契約（shared/・docs/04・DB）の変更要望 | ワーカー → **@manager** | マネージャーが裁定 or トーンさん経由で設計チャットへ |
| 部品の props 確定、「できたから使っていい」 | ワーカー → **相手ワーカーに直接** | 2者で完結。マネージャーを挟まない |
| 完了報告・ブロッカー | ワーカー → @manager | 完了は `notify_when_idle` で自動化も可 |
| 「このAPIどう使う」系の質問 | 相手ワーカーに直接 | マネージャーに来たら契約が不明瞭なサインとして記録 |
| 進捗の逐一報告・雑談 | **送らない** | トークンを消費するだけ |

**仕様はメッセージで送らない**。正本は docs/ と shared/。メッセージは「変化があった」という通知に留める。
目安：全フェーズ通して @manager が受けるのは 10〜20 通。これを超えていたら契約の書き方が甘い。

```

【役割】
```

## 6. 効率測定（「どの程度効率化できるか」の検証）

各フェーズで以下を記録する（トーンさんがメモ）：

| 項目 | 記録方法 |
|---|---|
| フェーズ0 所要時間 | 開始〜phase0タグまで |
| フェーズ1 各ワーカー所要時間 | 各タブの開始〜完了報告まで（5つ） |
| フェーズ1 壁時計時間 | 最初のタブ起動〜最後の完了報告 |
| 待ち時間 | トーンさんが「どのタブも待ち」だった時間（＝並列の恩恵） |
| コンフリクト数 | マージ時に手で解決した箇所数 |
| 依頼メモ数 | docs/requests/ のファイル数（＝契約の穴の数） |
| 結合バグ数 | フェーズ2で直した数 |

**比較の基準**：直列でやった場合の推定 ＝ フェーズ1各ワーカー所要時間の合計。
並列の効果 ＝ 合計 ÷ 壁時計時間。コンフリクト数と結合バグ数が「並列のコスト」。
これが 2 を超えていて、結合バグが 10 未満なら、本番チームでも同じ分割が使える判断材料になる。

## 7. 判断の記録

- **フロントは Vite + React**。理由：コンポーネント境界＝ファイル所有権の境界になり、並列開発と相性がいい。チームに推しログで経験者がいる。本番で変える場合は初回MTGで再判断
- **W4 は W5 の共通部品を待たない**。props だけ合わせて _stubs で進め、結合で差し替える
- **LiveKit のキー無しでも全ワーカー進められる**設計にした。W3 だけ疎通確認はキー取得後
- **DB は Railway の MySQL を全員で共有**（学校PCは Docker 不可）。migrate はトーンさんだけ。テストデータは名前に接頭辞
- 5タブは Claude Max の利用枠をかなり食う。枠が心配なら W4/W5 を先に、W1/W2 を次に、の**2波に分ける**
- **マネージャータブは「契約の番人＋結合担当」に限定**。横連絡はワーカー同士で直接行う
